# Detection coverage

This file is generated by `python scripts/gen_coverage.py` from the rules in `rules/`; a test
fails if it is out of date. Do not edit it by hand.

**How to read it.** A *detection rule* describes observable behaviour in telemetry. An *ATT&CK
technique* is a name for an adversary behaviour. A rule is mapped to a technique only when the
behaviour it looks for is an instance of that technique; a mapping never means the technique was
used, and unmapped rules are not less important. Techniques not listed here are **not covered**,
which is not the same as "absent" on your hosts. The tool does not claim complete ATT&CK
coverage, does not detect all macOS malware, and is not an EDR replacement.

Class: `heuristic` = rule inference needing validation; `ioc_match` = hit on an analyst-supplied
indicator; `baseline_change` = observed difference from a baseline (significance unknown).

## Per-rule notes

### MTH-BASE-001: New persistence artifact since baseline

New launch items, startup files and hooks are how persistence appears. Changes must still be matched to legitimate installs and updates.

Known false positives:

- Software installed or updated after the baseline was created.

### MTH-BASE-002: Persistence artifact modified since baseline

Modifying an existing launch item or startup file is a quiet way to change what runs automatically.

Known false positives:

- Legitimate software updates that rewrite their launch plists.

### MTH-BASE-003: Persistence artifact removed since baseline

Removal usually reflects an uninstall, but attackers also delete artifacts to hide activity.

Known false positives:

- Software that was uninstalled.

### MTH-BASE-004: Watched file modified since baseline

Changes to security-relevant configuration and watched executables should be explainable by an approved change.

Known false positives:

- OS and application updates, or approved configuration changes.

### MTH-BASE-005: New executable file in a watched location since baseline

New executables in watched writable locations are candidates for dropped payloads.

Known false positives:

- Software installers and build outputs.

### MTH-BASE-006: New listening service since baseline

New listeners change the host's remote attack surface and may represent backdoors or unauthorised services.

Known false positives:

- Developer servers and newly installed software.

### MTH-BASE-007: Recorded system configuration value changed since baseline

Changes to SIP, Gatekeeper, FileVault or firewall state alter the host's protections; OS version changes explain many other differences.

Known false positives:

- OS updates (version and build values change).
- Approved policy changes.

### MTH-CONF-001: System Integrity Protection or Gatekeeper reported disabled

SIP and Gatekeeper are core macOS protections. Disabling them is sometimes needed for development or debugging but it also lowers the barrier for malware, so the state is worth confirming against policy.

Known false positives:

- Kernel-extension, driver or security-research development machines.
- Lab hosts with documented exceptions.

### MTH-CONF-002: Application firewall or FileVault reported off

These are hardening controls, not indicators of malicious activity. They are reported so analysts can interpret other findings with the host's actual protection level in mind.

Known false positives:

- Many fleets rely on network-level controls and do not enable the application firewall.

### MTH-EXEC-001: Process executing from a user-writable location

Legitimate software is normally installed under /System, /usr, /Applications or a package manager prefix. Malware and droppers often execute from temporary or shared writable directories because they do not need privileges to write there.

Known false positives:

- Installers, updaters and app translocation run from temporary directories by design.
- Developer build outputs and test binaries executed from scratch directories.
- Software installed for all users under /Users/Shared in managed environments.

### MTH-EXEC-002: Script interpreter running a script from a writable location

Staged scripts dropped into temporary or shared directories are a common way to run attacker-controlled logic through trusted interpreters, which themselves look benign.

*Mapping justification:* The rule looks for a command or scripting interpreter executing a script file, which is the behaviour ATT&CK T1059 describes; it does not identify which interpreter technique.

Known false positives:

- Developers running scripts from Downloads or scratch directories.
- Automation tools that unpack helper scripts into temporary directories before running them.

### MTH-EXEC-003: Document or browser application spawning a shell or scripting host

These applications rarely start command interpreters directly. Malicious documents and exploited viewers commonly do, so the parent-child relationship is a useful hunting lead.

*Mapping justification:* A user-opened document or application launching an interpreter matches User Execution leading to Command and Scripting Interpreter use; the rule observes the relationship, not the document's content.

Known false positives:

- Office macros and add-ins used by IT automation or finance workflows.
- Browser extensions or helper apps that legitimately invoke osascript or shells.

### MTH-EXEC-004: Unsigned or ad-hoc signed executable outside trusted locations

Production macOS software is normally signed with a Developer ID or by Apple. Unsigned or ad-hoc binaries outside trusted prefixes deserve a look, although they are common for locally built tools.

Known false positives:

- Locally compiled developer tools, which are commonly ad-hoc signed on Apple Silicon.
- Scripts and open-source utilities installed outside a package manager.

### MTH-FILE-001: Recently modified executable in a writable location

Droppers and payload stages are often written to writable shared or temporary directories shortly before execution.

Known false positives:

- Build outputs, test fixtures and installers unpacked into temporary directories.

### MTH-FILE-002: Security-relevant configuration file with unexpected permissions

These files control privilege escalation, authentication and name resolution. Write access for unprivileged users lets them change security behaviour.

Known false positives:

- Deliberate admin-group access on lab hosts.
- Files created by configuration management with a service account owner.

### MTH-IOC-001: Process matches an analyst-supplied indicator

Indicator lists capture artifacts already linked to known activity. An exact match is a strong lead but depends on the quality and context of the indicator.

Known false positives:

- Reused or overly generic indicators (common process names, shared hashes).
- Stale indicators for software that has since been cleaned or legitimately reused the name.

### MTH-IOC-002: Persistence artifact matches an analyst-supplied indicator

Persistence mechanisms commonly reference payload paths, hashes or command-and-control addresses that appear in indicator lists.

Known false positives:

- Indicator values shared with legitimate software.

### MTH-IOC-003: Network connection or its process matches an analyst-supplied indicator

Contact with indicator addresses or domains, or traffic from an indicator process, links the endpoint to known infrastructure. The match does not show what data was exchanged.

Known false positives:

- Shared hosting or CDN addresses reused by legitimate services.
- Indicators that have been reassigned since publication.

### MTH-IOC-004: Observed file matches an analyst-supplied indicator

File hashes and paths from threat reports identify known artifacts when found on a host.

Known false positives:

- Path indicators for generic locations that legitimate software also uses.

### MTH-IOC-005: Command line or log message contains an analyst-supplied IP or domain

Scripts and tools often carry their download or command-and-control address on the command line or in log output.

Known false positives:

- Log messages that quote an address while blocking or documenting it.
- Security tooling that itself references indicator values.

### MTH-LOG-001: Repeated failed SSH authentication from one source

Bursts of failures from one address are consistent with password guessing against a reachable SSH service. The rule reports the burst, not whether any attempt succeeded.

*Mapping justification:* Repeated failed password authentications from one source match Brute Force: Password Guessing in form, though they may also come from misconfigured clients or scanners.

Known false positives:

- Vulnerability scanners and monitoring probes run by your own organisation.
- A user or automation with a stale saved password retrying.

### MTH-LOG-002: Repeated failed sudo authentication for one account

Several incorrect password attempts at sudo can indicate someone guessing an administrator password at an unlocked session, though mistyped passwords are the usual cause.

Known false positives:

- Ordinary typing mistakes, or password changes not yet propagated to the keychain.

### MTH-NET-001: Listening service not on the expected-process allowlist

Unexpected network listeners expand a host's attack surface and are used for bind shells, proxies or staging servers. Compare listeners with the baseline for stronger evidence.

Known false positives:

- Developer servers, file-sharing, AirPlay and local discovery services.
- Any application not yet on the allowlist for this fleet.

### MTH-NET-002: Established connection from a process in a writable location

Malware staged in temporary directories needs network access for command-and-control or tool transfer. The path is the signal; the destination alone is not treated as suspicious.

Known false positives:

- Installers and updaters downloading components while running from temporary directories.

### MTH-PERS-001: Launch item runs an executable from a writable location

Launch items run automatically at login or boot. Legitimate vendors install their helpers under /Applications, /Library or /usr/local. A launch item that runs a binary from a writable temporary location is a classic persistence pattern.

*Mapping justification:* A launchd property list that starts a program automatically is the persistence mechanism described by Launch Agent and Launch Daemon; which one applies depends on the plist's directory, shown in the evidence.

Known false positives:

- Per-user helper agents installed by software that runs from Downloads or temporary directories.
- Developer test jobs.

### MTH-PERS-002: Launch item references a missing executable

Orphaned launch items point at software that was removed, or at a payload that was deleted after installing persistence. Either case is worth confirming.

Known false positives:

- Leftover plists from uninstalled software.
- On-demand jobs whose binary is created at runtime.
- Programs on volumes that were not mounted during collection.

### MTH-PERS-003: Launch item outside the allowlisted vendors

Inventorying launch items that are not explicitly expected makes unknown persistence easy to review. This is an inventory lead, not a malicious-behaviour detection.

Known false positives:

- Any third-party software not yet added to the allowlist (VPN clients, backup tools, drivers).

### MTH-PERS-004: Launch item runs an inline shell or script command

Inline commands in launch items hide their logic in a plist and are used by persistence implants; they are less common in vendor-installed jobs.

*Mapping justification:* A launchd job whose action is an interpreter running an inline command combines launchd persistence with command and scripting interpreter use.

Known false positives:

- Vendor and IT management jobs that wrap commands in /bin/sh -c.

### MTH-PERS-005: Launch item in a system directory with unexpected permissions

Plists in system launch directories execute with elevated rights. If unprivileged users can modify them, they can be abused to run code with those rights.

Known false positives:

- Mis-installed third-party software that sets permissive modes.
- Admin-group-writable directories on some managed Macs.

### MTH-PERS-006: Shell startup file contains download, decode or reverse-shell style commands

Shell startup files run every time a shell opens, so attackers append commands there for persistence. Only suspicious-looking lines are recorded, never the whole file.

*Mapping justification:* Commands placed in shell startup files execute whenever a shell starts, which is Unix Shell Configuration Modification; the rule inspects only the file's current content.

Known false positives:

- Developer environments that call curl or wget for version managers and completions.
- Dotfile repositories that reference temporary directories.

### MTH-PERS-007: Login or logout hook configured

Login hooks are deprecated and rarely used by modern software; a configured hook runs a script as root at login or logout and is therefore worth reviewing.

*Mapping justification:* A LoginHook/LogoutHook entry in loginwindow preferences is the Login Hook technique itself; the rule reports its presence, not that it is malicious.

Known false positives:

- Legacy enterprise management tooling that still uses login hooks.

### MTH-SCRIPT-001: Download piped directly into a shell

Piping a download into a shell executes remote content without inspection. It is a common delivery method for droppers, though also a common installation idiom for legitimate tools.

*Mapping justification:* Fetching content from a remote host (Ingress Tool Transfer) and feeding it to a Unix shell (Unix Shell) is exactly what the matched pattern expresses.

Known false positives:

- Well-known installers documented as "curl ... | sh" (Homebrew, rustup, nvm).
- Administrators bootstrapping tooling from internal servers.

### MTH-SCRIPT-002: Base64-decoded content piped into a shell

Encoding a payload as base64 and decoding it into a shell hides the command from casual review and from simple string matching.

*Mapping justification:* Decoding an obfuscated payload (Deobfuscate/Decode, Obfuscated Files or Information) and executing it with a Unix shell is what the pattern describes.

Known false positives:

- Deployment scripts that unpack base64-embedded configuration or installers.

### MTH-SCRIPT-003: osascript requesting administrator privileges

AppleScript is a convenient way to prompt a user for credentials and then run commands as root. Malware uses this to escalate privileges after social engineering the password prompt.

*Mapping justification:* The pattern is AppleScript asking the user to authorise elevated execution, matching Elevated Execution with Prompt and AppleScript.

Known false positives:

- Legitimate installers and IT scripts that elevate through AppleScript dialogs.

### MTH-SCRIPT-004: Quarantine attribute removal

The quarantine attribute causes Gatekeeper to check downloaded files. Removing it lets unsigned or unnotarised downloads run without that check.

*Mapping justification:* Stripping the quarantine attribute is the documented way to bypass Gatekeeper checks on downloaded files.

Known false positives:

- Developers and power users clearing quarantine on trusted downloaded apps.
- Software deployment scripts for internally distributed applications.

### MTH-SCRIPT-005: launchctl loading a job from a writable location

launchctl registers launchd jobs, which is how Launch Agent and Launch Daemon persistence is activated. Jobs defined in writable temporary locations are unusual for managed software.

*Mapping justification:* launchctl load/bootstrap registers launchd jobs, the mechanism behind Launch Agent and Launch Daemon persistence; the rule cannot tell which of the two is being created.

Known false positives:

- Test harnesses and developers experimenting with launchd jobs.


## Known gaps

- No process-injection, kernel-extension, TCC/privacy-database, XPC, DMG/installer or browser
  extension telemetry; no file-write or process-exec event stream (collection is a point-in-time
  snapshot, so short-lived processes are missed).
- Login Items (Background Task Management) are not collected; only LaunchAgents/Daemons, startup
  items, shell startup files, login/logout hooks and the current user's crontab are.
- Network visibility is limited to `lsof` snapshots; unprivileged runs see only the caller's own
  sockets. No DNS, proxy or packet data. Domain IOCs match only when a hostname is present in the
  evidence (for example a log line or command line).
- Unified-log rules only see records inside the queried window and predicate; macOS redacts
  `<private>` fields and this tool cannot recover them.
- Code-signing context is `codesign -dv` metadata only; signatures are not cryptographically
  verified, and notarisation/Gatekeeper assessment is not performed.
- Rules are heuristics with documented false positives; tune allowlists in
  `configs/allowlists.yaml` for your fleet.
